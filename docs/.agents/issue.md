# Issue ledger（RSI 回路的登记面）

本仓缺陷与改进的唯一登记处，由 [rsi-hook](../../references/rsi-hook.md) 所指的 RSI 回路消费。编号 `RSI-xxx` 三位递增，从 RSI-001 起。

纪律：

- 发现即登记，新条目追加文件末尾；同一问题只维护一处，复发不新开编号（在原条目追加带日期的复盘点）；
- 条目字段六段式：表因 / 根因 / 定性 / 处理方式 / 后续防范 / 同类问题影响（可选）；
- 登记本身不等于启动处理——处理走 RSI 回路。

---

## RSI-001 配音机制深埋在视频流水线里，无法独立调用

**表因**：要把一句话配成 mp3，只能走 vibe-video 的整集流水线（`narration.json` → 逐句合成 → manifest），或手拼 `tts_sample.py`（仅 index-tts、依赖工作区路径、输出落在工程目录内）。edge 引擎没有任何「文本 → mp3」的独立入口，输出目录也没有环境变量可控。

**根因**：TTS 机制（风格预设、digest 缓存、文本归一化、服务端、客户端原语）是随视频流水线一起长出来的，从未与「逐句编排 + 时间轴」分层；`INDEXTTS_SERVER` 在 vibe-video 的 `config.py` 注册却没接进 `tts.py`（默认地址写死），说明机制层与编排层的契约本来就是松的。

**定性**：非阻断改进（机制缺口，不卡视频制作，但让配音能力无法复用）。

**处理方式**：抽成独立 Skill dub——`dub.py say` 以文本 + 风格产出 mp3，edge 与 index-tts 两引擎，输出到 `DUB_OUTPUT_DIR`；服务端 vendor 自 vibe-video 的 `tts_server.py`，仅把两处 `from tts import` 改指 `dub_tts_blocks`；摘要格式、风格预设与 vibe-video 逐字节同源，以黄金哈希钉死。vibe-video 同步改为委托 dub（另见其台账）。

**后续防范**：

- 机制原语只住 dub，vibe-video 不得再内联或另拷一份；黄金哈希与预设不变量的测试同样只住 dub（`tests/test_digest.py` 等），vibe-video 经委托自动继承，不留镜像副本；
- dub 的库模块一律 `dub_` 前缀，由 `tests/test_module_names.py` 钉死，防止 vibe-video 把 dub 的 `scripts/` 插进 `sys.path` 后同名模块互相遮蔽；
- 预设只增不改，改任一已上线预设的数值都会让已缓存音频全部失效。

**同类问题影响**：任何把「机制」和「编排」揉在一起的 Skill 都有同样的复用障碍；抽取时先找耦合点（本次只有 `tts_server.py` 对 `tts.py` 的两处 import）再决定切口，比先设计新接口更稳。

## RSI-002 首版评审揪出的四处边界缺口：孤儿进程、`--out-name` 逃逸、收尾吞结果、缓存键漏参

**表因**：[PR #1](https://github.com/ThreeFish-AI/dub/pull/1) 评审时发现四处低风险缺口，均不影响主路径：
1. 服务冷启动超时（或被 Ctrl-C 中断）后，已拉起的约 10 GiB 子进程无人回收，下次运行把它当「他人服务」复用，永远没人停；
2. `--out-name ../x` 可把成品写到输出目录之外；
3. 合成已成功、仅收尾 `stop_or_watch` 抛错（如 `lsof` 超时，`TimeoutExpired` 连 `main` 都捕不到）时，进程以非零退出且无回执，音频已落盘却报失败；合成失败叠加收尾失败时，根因被次生错误覆盖；
4. index-tts 的整段缓存键不含块间静音时长 `CHUNK_GAP_SEC`，日后调该常量会命中旧成品。

**根因**：「不误杀别人」被反复强化（按端口、校验 cmdline、去抖），但对称的「不漏收自己」没人设防；用户输入的文件名直接拼进路径而未过「纯文件名」闸；收尾被当成必然成功的尾部语句；整段键只组合了各块摘要，漏了拼接这一步自带的参数。

**定性**：非阻断（首版发布前补齐；其中 4 在 v0.1.0 前改键零成本，发布后再改会让已缓存的整段成品全部换名）。

**处理方式**：`start_server` 对自己持有句柄的子进程按进程组回收（SIGTERM → 逾期 SIGKILL，已退出则不发信号）并清 state 文件，超时与中断两条路径同一出口；`_resolve_dst` 拒绝含路径分隔符、`.`、`..`、空串的 `--out-name`（退出码 2，早于任何联网与拉服务）；`_teardown` 把收尾失败降级为 stderr 警告；`gap` 并入整段摘要。每项先写红测再改绿，并逐项撤销修复确认新测试变红。

**后续防范**：

- 凡「拉起」就要有对称的「收不回来时回收」，且只动自己持有句柄的进程，不按名字或端口找人；
- 凡拼进路径的用户输入，先过纯文件名闸再落盘；
- 收尾类语句不得改写主流程已确定的结果与根因；
- 整段缓存键 = 各块键 + 拼接阶段自带的全部参数，新增拼接参数时同步入键。

**同类问题影响**：任何「按需拉起长驻服务」的 Skill 都有孤儿风险，尤其冷启动慢、用户常中途 Ctrl-C 的；Ctrl-C 的 SIGINT 只送达终端的前台进程组，`start_new_session=True` 的子进程不在其中，必须由父进程显式回收。

## RSI-003 仓库与 Skill 更名 dub → vibe-tts：名称有四种形态，耦合点藏在行为里

**表因**：仓库名 `dub` 与「文本转语音」的能力语义脱节，统一更名 `vibe-tts`，波及本仓 317 处引用与三个跨仓未合并分支（vibe-video 委托层、rsi 注册档案、agents.md 枚举）。

**根因**：名称不只是文本，它以四种形态散布——仓库名/目录/skill 名（连字符 `vibe-tts`）、Python 模块前缀（下划线 `vibe_tts_`）、环境变量（`VIBE_TTS_*`）、以及藏在行为里的隐式耦合（缓存盐、状态文件 `by` 字段、slugify 兜底名、`.gitignore` 自嵌套守卫）。前三种靠有序替换可全量覆盖，第四种靠测试与台账才找得全。

**定性**：非阻断维护操作（v0.1.0 前执行，缓存盐更换与数据目录迁移零成本）。

**处理方式**：`git mv` 十个脚本 + 有序批量替换（URL → `dub_tts_*` 收敛 → `dub_` 前缀 → `DUB_` 变量 → `dub.py` → import/属性访问 → 裸词），历史台账两文件（CHANGELOG、本文件存量条目）不动；模块 stem 断言与裸模块标识符两处手工校准（`bare == ["vibe_tts"]`、`setattr(vibe_tts, …)`）；黄金哈希钉值零改动，269 测全绿即证跨仓同值未漂移。

**后续防范**：

- 仓库改名先建「形态映射表」再动手；裸词替换必须区分标识符与展示名两种语境（`setattr(dub, …)` 与 `prog="dub"` 的正确去向不同）；
- 与外部仓库共享的钉值（黄金哈希）在改名类操作中只改 import 不改值，测试全绿即零漂移证据；
- 落盘字段（缓存盐、状态文件 `by`）是隐式契约：改名前先停服务，避免旧状态文件不再被识别为「自己拉起」而漏收。

**同类问题影响**：任何 skill 化仓库的更名都遵循同一形态映射；跨仓引用在改名 PR 合并前都是未来态，合并顺序即一致性闸门。
